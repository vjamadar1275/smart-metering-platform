# ADR-0012: Phase 7 ML Model Framing on Synthetic Data, and Structural (Not Keyword) SQL Safety for the NL Agent

## Status
Accepted

## Context
Phase 7 requires four models (leak detection, demand forecasting, anomaly detection, predictive maintenance) plus an NL analytics agent that generates and executes SQL against Gold, per ADR-0008. Two problems recur across all of it:

1. **No real ground truth.** This platform has no confirmed-leak log, no real demand-forecast actuals beyond what the synthetic generator produces, and no real meter-failure/replacement history. Every model needs a training target, and none of the "obvious" targets (is this a real leak? did this meter actually fail?) exist as real labels anywhere in this repository.
2. **The NL agent executes model-generated SQL.** A foundation model (reached through Databricks' governed external-model proxy per ADR-0008) writes a query from a natural-language question; that query then runs against a real SQL Warehouse. Whatever validates that query before execution is the only thing standing between "the model wrote something reasonable" and "the model wrote (or was prompt-injected into writing) something that reads data it shouldn't."

## Decision

**Models (ground truth):** Frame each model around what the synthetic data can actually support, not around the more ambitious question ARCHITECTURE.md's phrasing evokes — and say so in each model's docstring:
- **Leak detection**: unsupervised (IsolationForest) over per-meter night-flow features, not a classifier — there is no confirmed-leak label to classify against.
- **Demand forecasting**: supervised regression, but the *target* is the platform's own next-day actual consumption (a real, available label) — this is the one model of the four with a genuinely real supervised target.
- **Anomaly detection**: unsupervised (IsolationForest), explicitly scoped as a broader complement to `gold.daily_usage.usage_anomaly_flag`'s spike-only rule, not a replacement for it.
- **Predictive maintenance**: supervised classification, but the label is "will this meter's battery cross 15% within 30 days" (derived purely from each meter's own future battery trajectory in historical data) — not "will this meter fail," which this platform has no record of.

**NL agent SQL safety:** Validate generated SQL via a real SQL parser (`sqlglot`), checking parsed statement *type* (must be `SELECT`/`UNION`) and parsed table references' schemas (must be `gold`/`reference`), not a keyword/regex blocklist.

## Rationale

- **Why not invent synthetic failure/leak-confirmation labels to enable "proper" supervised models**: a supervised model trained on invented ground truth would report precision/recall numbers that look real but measure nothing about the world — worse than an honestly-unsupervised model, because the metrics *look* trustworthy enough to be relied on. Framing leak detection and anomaly detection as unsupervised anomaly scoring is a smaller, true claim rather than a larger, fabricated one.
- **Why demand forecasting is the one place supervised learning was used**: "will tomorrow's consumption look like today's, last week's, and the trailing average" has a real, non-invented target — the platform's own future consumption, which the historical data genuinely contains. This is a case where supervised learning is honestly available, so it's used, rather than defaulting to unsupervised everywhere for consistency's sake.
- **Why predictive maintenance's label is "battery will get low," not "meter will fail"**: a real predictive-maintenance system predicts failure/replacement need from a maintenance log this platform doesn't have. "Will cross the low-battery threshold" is a strictly narrower, mechanically derivable claim from data that genuinely exists (the battery trajectory itself) — a real technique (this is a legitimate class of synthetic/proxy labeling used in production predictive-maintenance systems too, when a leading indicator is a reasonable stand-in), but the model's documented scope must match what it was actually trained to predict.
- **Why `sqlglot` over a keyword blocklist for the NL agent (vs. option: regex-based keyword/schema matching)**: an early implementation of `validate_readonly_query` used exactly this — `re.search(r"\bdrop\b", ...)` plus a schema-reference regex — and it was **caught by this ADR's own test suite** rejecting a syntactically valid, safe query (`SELECT m.dma_id FROM reference.dim_dma m`) because the regex couldn't distinguish a table alias (`m.dma_id`) from a schema-qualified reference (`reference.dim_dma`) — both match `\w+\.\w+` identically. That failure mode generalizes in the dangerous direction too: a regex that can't tell an alias from a schema reference also can't reliably guarantee it *catches* every real schema reference in an adversarial or merely awkwardly-phrased query. Real SQL parsing (`sqlglot.parse` into an AST, then walking `exp.Table` nodes with their resolved `.db`) removes this entire class of ambiguity — the parser already knows the difference between an alias and a schema-qualified table because it has to, to parse the query at all.
- **Why statement-*type* checking (must be `exp.Select`/`exp.Union`) instead of a forbidden-keyword list for DDL/DML**: the same ambiguity problem applies — a keyword blocklist for `DROP`/`INSERT`/etc. is both bypassable (obfuscation, or a keyword appearing inside a string literal or a legitimately-named column like `updated_at`) and a source of false positives. Checking what kind of statement the parser actually produced is structural, not textual, and doesn't have either failure mode.

## Consequences

- Every model's docstring and the KPI glossary (`docs/glossary/kpi_glossary.md`) explicitly state the narrower, honest claim each model actually supports — a future reader (or the NL agent itself, via RAG grounding) sees "predicts battery will get low" and "estimated NRW, not measured," not an inflated claim.
- `src/ml/agent/nl_analytics_agent.py` takes a real dependency on `sqlglot` (added to `requirements-dev.txt` and `bundles/model_serving.yml`'s environment spec) — a small, well-established, pure-Python addition, justified by removing a security-relevant class of bug the regex approach demonstrably had.
- None of the four models have been trained against real production data or validated by a subject-matter expert (a water-utility engineer confirming a flagged "leak" is real) — that validation loop doesn't exist yet and can't, absent real historical incident data. This is the natural next open item once this platform (or a pilot of it) has real operational history to learn from, not something Phase 7 can close on its own.
- The NL agent's model-serving/Vector-Search wiring (the actual Databricks API calls in `sync_vector_search_index` and whatever calls the chat-completions endpoint) is unexercised by this repository's test suite, which only covers the injected-collaborator orchestration logic and the SQL safety validation — deliberately, since neither a live Vector Search index nor a live Model Serving endpoint exists in this sandboxed development environment (see the repository's other Phase 6/7 "not mechanically validated live" caveats for the same reason).
