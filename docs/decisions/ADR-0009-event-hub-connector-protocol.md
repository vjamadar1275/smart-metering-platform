# ADR-0009: Kafka Protocol for Spark Consumption, Native AMQP for Producers

## Status
Accepted

## Context
Azure Event Hubs exposes two protocols relevant to this platform: native AMQP 1.0 (Azure's first-party protocol, used by the Azure SDKs and by Azure's own Schema Registry), and a Kafka-compatible endpoint (Event Hubs impersonates a Kafka broker on port 9093). Bronze's Structured Streaming job (the consumer, reading into Databricks) and the field-gateway/simulator (the producer, writing into Event Hubs) don't have to use the same protocol, and the right choice differs for each side.

## Decision
- **Spark Structured Streaming (Bronze consumer)** reads via the **Kafka connector** (`format("kafka")`) against Event Hubs' Kafka-compatible endpoint.
- **Producers** (the Event Hub simulator in this repo, and — by extension — real field gateways) publish via the **native AMQP 1.0** `azure-eventhub` SDK.

## Rationale

- **Consumer side — Kafka connector**: Databricks Runtime ships Spark's Kafka connector as a first-class, actively maintained component with mature support for `maxOffsetsPerTrigger` rate limiting, offset-based exactly-once semantics, and AQE-aware partition handling — all of which this pipeline depends on (see [ARCHITECTURE.md § capacity planning](../architecture/ARCHITECTURE.md#capacity-planning) for the throughput this needs to sustain). The older `azure-eventhubs-spark` connector (native AMQP, Event Hubs-specific) is a smaller, less actively maintained library with a materially smaller user base exercising it at Databricks' scale. Since Event Hubs' Kafka endpoint is a fully supported, Microsoft-documented integration path (not an unofficial workaround), there's no reliability trade-off in choosing it — only an upside in tooling maturity.
- **Producer side — native AMQP**: producers benefit from Event Hubs' AMQP-native features that don't have a Kafka-protocol equivalent on Event Hubs: explicit `partition_key` control that Azure guarantees maps consistently to a partition (used here to key by `meter_id`, so per-meter ordering holds — see [ARCHITECTURE.md § Field → Ingestion](../architecture/ARCHITECTURE.md#1-field--ingestion)), and lower per-message overhead for the small (~350 byte) payloads this platform sends at high volume. Real field gateways in production would also most naturally speak AMQP, as that's what embedded/IoT-oriented Event Hubs SDKs and firmware libraries target first.
- **Schema Registry stays AMQP-only, by design**: Azure Event Hubs' Schema Registry integration is built for AMQP producers/consumers (schema ID embedded in the AMQP message), and does not integrate with the Kafka protocol path the same way Confluent's Schema Registry integrates with Kafka's wire format. Rather than forcing a Confluent-style setup Azure doesn't natively support, this platform's Kafka-side consumer (Bronze) parses Avro bytes against the static schema file in `schemas/avro/meter_telemetry.avsc` (the same schema registered in the Schema Registry group, kept in sync manually/by CI at deploy time — see [event-hub module README](../../terraform/modules/event-hub/README.md)), rather than doing a registry lookup per message. This is a reasonable trade because Bronze's own permissive schema-evolution model (ADR-0002, ARCHITECTURE.md § Bronze → Silver) already tolerates a producer briefly running a newer schema version than the static file the consumer was deployed with — new optional fields simply pass through until the consumer is redeployed with the updated schema file.

## Consequences

- Two different SDKs/protocols are used for one Event Hub, which is slightly more surface area than a single-protocol design — accepted because each side's protocol choice is independently the stronger option for what that side does, and both are officially supported integration paths for the same underlying Event Hub (no forked infrastructure).
- The static schema file must be kept in sync with what's registered in the Schema Registry group; a process gap here (schema file updated but not the registry, or vice versa) wouldn't break Bronze (Avro's Backward compatibility rules mean old and new schemas can usually still parse each other's optional-field-only changes) but would break schema-registry-based tooling that expects the registry to be authoritative. This is called out as an operational risk to close out with automation in Phase 8, not deferred silently.
- Consumer authentication (Kafka SASL/PLAIN using the namespace connection string, stored in Key Vault — see [event-hub module](../../terraform/modules/event-hub/main.tf)) is a materially different auth mechanism than producer authentication (AMQP SAS token/connection string via the `azure-eventhub` SDK), which the deployment tooling (Phase 8 CI/CD, secret rotation runbooks) must account for as two separate credentials to rotate, not one.
